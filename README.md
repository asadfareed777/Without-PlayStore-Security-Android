# Secure Keys Demo — Android (Kotlin + C++/NDK, XOR-encoded constants)

A small demo app that shows how to keep **`BASE_URL`**, **`IV`** and **`SECRET`**
out of Kotlin/Java code and out of plain-text strings in the APK. Their values live
in a C++ library as **XOR-encoded bytes**, get decoded at runtime, and are loaded into
`AppConstants` **once, when the app starts**.

> ⚠️ **Demo only.** Anything shipped inside an APK can be recovered by a determined
> attacker (debugger, Frida, memory dump). This technique raises the bar against
> casual reverse engineering (`strings`, jadx, apktool). It does **not** replace
> server-side secrets, token exchange, or Play Integrity / attestation. See
> [Limitations](#limitations).

---

## How it works

```
secrets.demo.properties  (or secrets.properties)   (plaintext — build-time input only)
          │
          │  Gradle task :app:encodeSecrets   (runs automatically before the CMake build)
          ▼
app/src/main/cpp/generated/obfuscated_secrets.h   (XOR bytes + random key, no plaintext)
          │
          │  CMake / NDK
          ▼
libappcore.so  ──JNI_OnLoad──► RegisterNatives(NativeKeys, …)
          │
          │  SecureKeysApp.onCreate()  →  AppConstants.init()
          ▼
AppConstants.BASE_URL / IV / SECRET    (used anywhere in Kotlin)
```

### 1. Encoding (build time) — `encodeSecrets` task in `app/build.gradle.kts`

The encoder is plain Kotlin inside the Gradle build script, so you don't need Python or any
other tool. `preBuild` and the CMake tasks depend on it, so every normal build
(Android Studio **Run**, `assembleDebug`, …) generates the header first.

For every value, byte `i` is encoded as:

```
enc[i] = plain[i] ^ KEY[(i + salt) % 32] ^ ((i * 31 + salt) & 0xFF)
```

| Part   | What it is                                                        |
|--------|-------------------------------------------------------------------|
| `KEY`  | random 32-byte key (`SecureRandom`), **regenerated whenever the task re-runs** |
| `salt` | random byte per value, so equal strings never encode the same way |
| `i*31` | position-dependent mask, so repeated characters don't repeat in output |

Gradle's up-to-date check skips the task (and keeps the current key) unless the secrets
file or the JNI names change. That keeps native builds incremental.

The task encodes **all** strings the C++ code needs — not only the three secrets
but also the JNI class name, method names and method signature. Running
`strings libappcore.so` reveals none of them.

### 2. Decoding (runtime) — `app/src/main/cpp/`

| File                              | Role |
|-----------------------------------|------|
| `generated/obfuscated_secrets.h`  | Generated by Gradle: encoded byte arrays, lengths and salts. Git-ignored; never edit by hand. |
| `xor_decoder.h`                   | `obf::decode()` reverses the formula. It reads the key through a `volatile` pointer so the compiler can't pre-compute the plaintext at build time. `obf::wipe()` zeroes buffers afterwards. |
| `native-lib.cpp`                  | `JNI_OnLoad` decodes the JNI names, calls `RegisterNatives`, then wipes them. Each native getter decodes → `NewStringUTF` → wipes. |
| `CMakeLists.txt`                  | `-fvisibility=hidden`, `--exclude-libs`, `-s`: only `JNI_OnLoad` is exported; there are no `Java_com_demo_…` symbols to search for. |

### 3. Startup (Kotlin) — `app/src/main/java/com/demo/securekeys/`

| File               | Role |
|--------------------|------|
| `NativeKeys.kt`    | `internal` JNI bridge; loads `libappcore.so`, declares `external fun nativeBaseUrl/nativeIv/nativeSecret`. |
| `SecureKeysApp.kt` | `Application.onCreate()` → `AppConstants.init()`, which runs before any Activity. |
| `AppConstants.kt`  | Holds `BASE_URL`, `IV`, `SECRET` (+ `IV_BYTES`, `SECRET_BYTES`). Setters are private and it's initialised once. |
| `CryptoHelper.kt`  | Example consumer: AES/CBC/PKCS5 using `SECRET` as the key and `IV` as the IV. |
| `MainActivity.kt`  | Shows the loaded values (IV/SECRET masked by default) and an encrypt → decrypt round trip. |

Using the constants anywhere in the app:

```kotlin
val retrofit = Retrofit.Builder()
    .baseUrl(AppConstants.BASE_URL)
    .build()

val key = SecretKeySpec(AppConstants.SECRET_BYTES, "AES")
val iv  = IvParameterSpec(AppConstants.IV_BYTES)
```

## Requirements

- Android Studio (Ladybug or newer), or JDK 17–21 for command-line builds
- Android SDK 36, **NDK 27.0.12077973**, **CMake 3.22.1** (SDK Manager → SDK Tools)

Toolchain: AGP 8.13.0, Gradle 8.13, Kotlin 2.1.21, minSdk 24, targetSdk 36.

> Gradle 8.13 can't run on JDK 25. If your default `java` is 25, build from Android
> Studio, or point `JAVA_HOME` at Android Studio's bundled JBR.

## Running the demo

**Android Studio:** open the folder, let Gradle sync, then press **Run**.

**Command line:**

```bash
./gradlew :app:installDebug
```

The app shows `BASE_URL`, plus masked `IV` and `SECRET`. Tap **Reveal** to see them in full, and **AES encrypt → decrypt** to check the round trip.

Logcat (debug builds only):

```
D/SecureKeysApp: Constants loaded from native layer. BASE_URL=https://api.demo-server.com/v1/
```

## Changing the values

1. Copy the demo file. `secrets.properties` is git-ignored, and the build uses it automatically when it exists:
   ```bash
   cp secrets.demo.properties secrets.properties
   ```
2. Edit `BASE_URL`, `IV` (exactly 16 bytes) and `SECRET` (16, 24 or 32 bytes for AES).
3. Rebuild the app. The header is regenerated with a **new random XOR key** because the input changed.

To rotate the XOR key without changing any values:

```bash
./gradlew :app:encodeSecrets --rerun-tasks
```

### Adding a new constant (e.g. `API_KEY`)

1. Add `API_KEY=...` to the properties file, and add `"API_KEY"` to the `required` list in `EncodeSecretsTask` (`app/build.gradle.kts`).
2. Add `"JNI_M_API_KEY" to "nativeApiKey"` to the `jniStrings` map in the same file.
3. In `native-lib.cpp`, add a getter that returns `toJString(env, OBF_DECODE(API_KEY))`, and add a matching
   `{mApiKey.c_str(), sig.c_str(), …}` entry to `methods[]`. Decode `mApiKey` from `JNI_M_API_KEY` and wipe it, the same way the other names are handled.
4. In Kotlin, add `external fun nativeApiKey(): String` to `NativeKeys`, plus a property set in `AppConstants.init()`.

## Verifying the obfuscation

After a release build:

```bash
./gradlew :app:assembleRelease
unzip -o app/build/outputs/apk/release/app-release.apk "lib/arm64-v8a/*" -d /tmp/apk
strings /tmp/apk/lib/arm64-v8a/libappcore.so | grep -iE "demo-server|Dm0Iv|Dem0_S3cret|NativeKeys|nativeSecret"
# → no output: none of the plaintext is in the binary
```

With the NDK's `llvm-nm -D`, the only app symbol you'll see exported is `JNI_OnLoad`.

## Limitations

This demo is honest about what it does and doesn't protect against.

| Protects against | Does **not** protect against |
|---|---|
| `strings` / grep on the APK or `.so` | Hooking `NativeKeys.native*()` or `AppConstants` with Frida/Xposed |
| Decompiling Kotlin with jadx (no constants in the dex) | Reading process memory: the values are `String`s on the JVM heap once loaded |
| Finding JNI functions by their exported `Java_…` names | Static reversing of the XOR routine, which is symmetric, with the key next to the data |
| Accidentally committing secrets in Kotlin source | Repackaged or tampered APKs; add signature / integrity checks for that |

For production, consider:

- Keep real secrets **on the server**, and have the app get short-lived tokens after authentication or attestation (Play Integrity API).
- Add APK signature checks, root/debugger/Frida detection, and certificate pinning.
- Use a stronger native obfuscator (e.g. O-LLVM, or commercial tools) on top of this.
- Use **unique random IVs per encryption** in real AES-CBC/GCM usage. A fixed IV is used here only to demonstrate passing constants around.
